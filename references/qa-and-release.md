# 验收与发布

选与本次改动相关的检查；小改动不必重跑无关的昂贵流程。修改构建结果后，旧报告不能充当新版本通过的证据。

## 交付形式先分清

| 形式 | 重点验证 | 不能据此声称 |
| --- | --- | --- |
| 本地网站文件夹 | 相对资源路径、启动说明、依赖 | 已有公开网址 |
| 独立 HTML | 嵌入资源、移动后/离线打开、文件大小 | 每个手机文件预览器都支持脚本 |
| 托管网站 | 真实 URL、资源、HTTPS、深链接刷新 | 仅本地成功就算部署完成 |
| GitHub 开源仓库 | 真实账号、远端提交、关键文件、可见性 | 有本地 commit 就已开源 |

`file://` 下的 fetch、模块和跨源行为与服务器不同，最终分享形式需要独立验收。Base64 嵌入会增加文件体积；不要无条件把大模型塞进单文件。

## 可观察的验收

- 桌面及窄屏：至少实际查看一个手机宽度（如 390px），必要时检查 320px。长标题、翻译和联系方式不溢出；按钮可触达。
- 导航：首页→列表→详情→返回，关于、联系、浏览器后退与刷新都符合预期。外链目的地正确。
- 互动：触屏不被拖动模型锁住；重复点击和中断后能恢复；图片大图可关闭；键盘与焦点可用。
- 内容：概念与成果状态准确；中英切换覆盖新增文本；品牌和联系方式没有被意外改动。
- 资源：图片、字体、脚本、模型成功加载；无阻断性控制台错误；需要离线的产物不依赖联网资源。
- 交付：对最终文件重命名、移至独立目录后再打开；通过模拟只能声称“手机尺寸/触屏模拟通过”。有真机检查再说明设备。

保存简短结果与截图或自动检查报告（如有），写明检查对象和限制，不用“全部完美”代替证据。

## 发布 GitHub

仅在用户授权的范围发布。公开内容先单独整理进目录，排除密钥、私密联系方式、原始聊天、PPT、未授权图片和大型个人模型。

常规步骤：检查 git 状态 → 确认登录账号 → 确认目标仓库 → 提交 → 常规推送 → 检查远端 SHA、关键文件与仓库可见性。新建仓库与更新现有仓库分开判断；不能因网络错误就认定仓库不存在。不要强制推送去覆盖未理解的远端历史。

登录或网络失败时保留本地提交、操作指南和真实的待发布状态。发布成功后才将网站改为“已在 GitHub 开源”，附可访问的仓库链接。创建仓库成功但推送失败也要分开记录。

## 迁移与维护

按用户要求选择主目录，区分源码、素材、构建输出、备份和分享版。迁移时先复制、核对并重新打开入口，确认后才按授权清理明确的旧目录。不要根据相似名称递归删除。

交付时记录：哪一个文件是入口、怎样更新一个项目、需要运行哪些构建命令、最后一次检查了什么、发布到哪里。可使用交接模板。
