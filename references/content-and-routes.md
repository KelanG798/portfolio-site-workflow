# 内容与页面结构

## 从零散资料提炼项目故事

先列事实，再写展示文案。一个简短项目故事可以包含：

- 为什么做：具体观察到的困难，避免泛泛的“赋能未来”。
- 为谁做：目标人群与使用情境。
- 想怎么解决：一句话讲清方案；把远期设想留在路线图里。
- 我做了什么：将个人工作与团队工作分开。
- 现在到哪一步：调研、定义、原型、概念验证或上线，使用实际状态。
- 有什么依据：已有问卷、分析、原型、演示、代码或测试；没有的数据不补写。
- 下一步：如果用户希望展示，可以简述仍需验证的部分。

不必每项都成为大段文字。卡片可以只显示名称、一句话价值、阶段和详情按钮。详情再展开证据与职责。不要为了模板完整而制造空白模块。

## 页面选择

| 页面 | 应回答的问题 | 常见边界 |
| --- | --- | --- |
| 首页 | 你是谁，关注什么，从哪里继续看？ | 不重复全部项目详情 |
| 项目列表 | 有哪些作品，哪个值得打开？ | 卡片简介控制长度 |
| 项目详情 | 为什么做，你贡献什么，证据和阶段是什么？ | 区分目标与实现 |
| 关于 | 背景、兴趣、工作方法是什么？ | 不把兴趣写成已证明的能力 |
| 联系 | 如何找到你？ | 邮箱与 GitHub 可独立成栏 |
| 成果/开源 | 有什么可查看、可验证的输出？ | 提供真实链接与状态 |

这些是可选结构，不要求六个独立页面。若用户明确要求点击后换到另一页，就不要用强制滚动替代。

## 可持续新增项目

使用稳定 id 与独立 route；标题修改时尽量保留地址。先检查现有登记方式，再决定使用 JSON、Markdown、CMS 或静态 HTML。不要同时建立互不相通的两套项目数据。

建议记录字段：`id`、`title`、`summary`、`stage`、`role`、`evidence`、`media`、`route`。双语时为需要翻译的文本保存语言字段。没有媒体的开源成果可以用文字卡片与图标，不应被图片必填规则卡住。

新增流程：导入用户资料 → 提炼事实 → 复用详情模板 → 更新列表 → 检查路由与双语 → 重建分享版。更新同一 id 应更新原项目，避免重复条目。

## 检查文案是否像本人

用用户的表达和真实动机写开头。具体说“我负责问卷设计和用户画像”，比“具备端到端创新能力”更容易判断。删掉没有证据的高级形容词、重复价值口号和假想的用户反馈。
